# 真实讨论对话验收场景

以下是验收条件，不是已执行的模型测试结果。用已启用 Task Clarifier 且关联工作对话的测试聊天检查；只读项目，提示词不派发。每轮先检查实际 `read_thread` 结果，再检查回答。脚本测试只能验证提醒与状态，不能证明模型执行了读取或及时交稿。

| 场景与输入 | 应观察到的行为 |
|---|---|
| 关联工作对话已有存档管理讨论；问“这个功能主要解决什么问题？” | 本轮读取后答疑，解释基于实际来源；尚无明确工作目标时不强制塞执行稿。 |
| 补充“自动与手动都是 APP 存档，同等管理；管理页不新建、不读取；我希望重视这个功能，有完整需求文档” | 维持讨论模式，交让工作对话整理需求文档的提示词及选型；无需先讨论文档中每条规则，不直接展开完整文档。 |
| 明确说“接下来我需要你写一份完整存档管理需求文档” | 当轮提示词、具体模型和强度齐全；提示词保留已定范围，未知规则作为待确认项，不再问是否需要提示词。 |
| 新一轮纠正“删除前自动备份还没确定，不要作为既定需求” | 本轮重读，给完整精简修订稿；撤销未确认规则，保留自动/手动同等管理和不新建/读取等兼容条件。 |
| 说“先别出提示词，先给我说方案，我确认后再写” | 本轮读取后讨论方案，遵守暂不交稿边界；用户确认后及时交稿。 |
| 说“优化这个功能”，但关联记录有两个可能对象，当前上下文无法定位 | 问一个定位目标的关键问题；不擅选对象，也不追问普通实施细节。若用户明确索要提示词，交标明目标缺口的临时稿。 |
| 关联工作对话读取失败；明确要求交执行稿 | 披露不能确认的最新状态，基于已知要求交标注缺口的临时提示词；不虚构进度，也不因普通未知项无限等待。 |
| 说“下一步”，工作对话显示上一份需求文档正在撰写或已完成 | 说明当前状态；不再次安排同一撰写任务。真正需要新动作时交能推进原目标的提示词，失败重试须有新证据或方法变化。 |
| 压缩或恢复后说“按这个改”，已有稿与关联可以恢复 | 不要求重新点名 Skill；重新取得本轮工作上下文，保留已有约束并交精简完整修订稿。正文确已丢失时索取最小缺口，不编造。 |

精简检查：第一句明确结果；保留会改变范围或结果的约束；没有整段历史、重复要求、模型选型研究或无必要流程。给同一工作对话的稿不重复它已有的背景，给新对话则补足定位信息。记录实际回答与工具调用，并把未通过项与脚本故障分开报告。
